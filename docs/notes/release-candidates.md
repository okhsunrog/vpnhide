# TODO: release-candidate builds (`vX.Y.Z-rc.N`)

Status: **not started**. Written 2026-09-17 after v1.3.0 shipped as a GitHub
pre-release on a final tag. This note records what a proper rc flow needs so
it can be picked up without re-deriving it.

## What we do today

- `release.py X.Y.Z` bumps every version, rotates `changelog.d/` into
  `changelog.json` and regenerates `CHANGELOG.md`; the maintainer tags the
  merge commit and CI's `release` job creates a **draft** release with the
  assets and the `## vX.Y.Z` section of `CHANGELOG.md` as notes.
- To let testers try a build before everyone gets it, the maintainer publishes
  that draft with **Set as a pre-release** and without **Set as the latest
  release**. `releases/latest` keeps pointing at the previous version, so the
  in-app `UpdateChecker` (which reads `releases/latest`) and the module
  managers (`update-json/*.json`, only regenerated by `scripts/update-json.sh`
  after the final publish) do not see it.
- When testers are happy: edit the release, drop pre-release, set latest, run
  `./scripts/update-json.sh`, commit `chore: update-json for vX.Y.Z`.

The limitation: the tag is already the final `vX.Y.Z`. A bug found during
testing cannot be fixed "inside" that version; it becomes `X.Y.Z+1`.

## Target flow

Standard semver pre-release tags, as most projects do it:

```
v1.4.0-rc.1   → GitHub pre-release, testers install it
v1.4.0-rc.2   → only if rc.1 needed fixes
v1.4.0        → final, on the same commit as the last rc (or the fix commit)
```

Ordering per semver: every `-rc.N` sorts below the final, `rc.2` above
`rc.1`. Label meaning: `alpha` = feature-incomplete, `beta` = complete but
untested, `rc` = believed ready and becomes the final unchanged if nothing is
found. For a short tester round before each release, `rc` is the right label.

## What already works

- The CI trigger `refs/tags/v*` matches `v1.4.0-rc.1`, so the `release` job
  runs and builds every asset.
- `git describe --tags --match 'v*'` in `scripts/build_lib.py` picks the rc tag
  up, so intermediate builds after it are stamped `1.4.0-rc.1-3-g<sha>`.
- Cargo accepts `1.4.0-rc.1` as a crate version; `module.prop` `version=` and
  the Gradle `versionName` are plain strings.
- The in-app updater reads `releases/latest`, which never returns a
  pre-release, so rc releases stay invisible to ordinary users without any
  code change. `update-json/` is only touched after the final publish.

## What blocks it

1. **`versionCode` has no room for an rc.** `scripts/release.py` derives
   `major*10000 + minor*100 + patch` (mirrored in the module.prop files and
   `lsposed/app/build.gradle.kts`). `rc.1`, `rc.2` and the final `1.4.0` would
   all be `10400`. Android allows reinstalling the same code, but the module
   managers only offer an update when the code grows, so a tester on `rc.1`
   would never be offered `rc.2` or the final through `update-json`. Today
   that is masked because `update-json` only ever points at finals; it becomes
   a real problem the moment a beta channel exists.
   Proposed scheme: `major*100000 + minor*1000 + patch*10 + stage`, with
   `stage = N` for `rc.N` (1..8) and `9` for the final. Codes stay monotonic
   across the switch (`1.3.0` is `10300` today; `1.4.0-rc.1` → `104001`,
   `1.4.0` → `104009`). The formula lives in `release.py`; the `versionCode`
   comment in `build.gradle.kts` must follow.
2. **`release.py` rotates the changelog unconditionally.** For an rc the
   fragments in `changelog.d/` must survive (more may land between rc.1 and
   the final). Needed: `release.py 1.4.0-rc.1` patches versions only, does not
   rotate, and writes the rc notes from the pending fragments (what
   `./scripts/preview-changelog.py` prints) somewhere the CI job can pick up.
   `VERSION_RE` in `release.py` currently rejects anything but
   `MAJOR.MINOR.PATCH`.
3. **The `release` CI job extracts notes by `## <tag>` from `CHANGELOG.md`.**
   No such section exists for an rc, so the notes would be empty. Either the
   job falls back to the pending-fragment preview when the tag has a
   pre-release suffix, or `release.py` commits a generated `RELEASE_NOTES.md`
   for rc tags.
4. **`docs/releasing.md`** documents one flow; it needs the two-step rc →
   final flow and the promotion checklist above.
5. **Device check.** Confirm on one Magisk, one KernelSU-Next and one APatch
   install that the managers compare the new six-digit codes as expected
   (`104001 < 104009`, and `10300 < 104001` for people upgrading from 1.3.0).

## Not in scope here

A separate stable/beta **update channel** (own `update-json` set, a channel
switch in Settings, CI publishing beta builds) is the Magisk-Canary /
KernelSU-Next / LSPosed-CI model. It is the better long-term answer for a
standing tester group and would reuse the rc tags above for its builds, but it
is a larger change and is tracked separately if it is ever wanted.
