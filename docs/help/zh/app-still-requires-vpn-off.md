# 应用仍要求关闭 VPN

如果某个应用一直以“VPN 处于活动状态”为由拒绝运行，在断定它坏掉之前，先按下面
逐条排查。

## 排查清单

1. **对的应用、对的角色。**把角色赋给发出抱怨的那个应用——不是你的 VPN
   客户端——并同时给它 **Java** 和 **Native**。见[设置隐藏](configure-hiding.md)。
2. **对的资料。**在主资料里配置；见
   [工作资料、克隆与第二空间](work-profiles.md)。
3. **保存后重启应用。**强制停止目标应用再重新打开，让它对照隐藏后的视图重新
   检查——运行中的应用可能缓存了旧答案。见[更改何时生效](saving-applying.md)。
4. **它在扫描 VPN 应用吗？**如果它查看已安装的包，开启 **Apps** 角色并确保你的
   VPN 客户端已被隐藏。
5. **它在探测 localhost 吗？**如果你运行本地代理/VPN 守护进程，加上 **Ports**
   角色。
6. **Zygisk + 银行应用？**如果你的后端是 Zygisk，且开启 Native 让情况更糟，就对
   该应用关闭 Native，改依赖 Java。

## 隐藏在起作用，但应用仍拒绝

运行[诊断](vpnhide://diagnostics)。通过只证明在 VPN Hide 自身 UID 下运行的检查，
不证明每个目标应用都看到同样的结果。比较目标的角色、自定义钩子、资料和路由。
不同的 API 调用顺序或未经测试的检测方法也可能暴露隐藏缺陷；报告中应保留这种可能，
不要将所有拒绝都归为 VPN Hide 无法处理的原因。

其他可能原因包括：

- **服务器端检查。**服务看到的是你的出口 IP。如果该 IP 属于已知的 VPN/主机托管
  段，无论设备报告什么它都可能封你——把该应用改为**直连**而非走隧道。见
  [第三方检测器仍发现 VPN](tester-finds-vpn.md)。
- **超出当前后端覆盖范围的检测路径。**诊断会把它们标为*“未覆盖”*（Not
  covered）。内核后端或实验性保护也许能多堵一些——见
  [能力与限制](capabilities-limits.md)。
- **缓存结果。**重启应用（必要时还有你的 VPN）再检查一次。

如果以上都无法解决，[收集调试报告](collect-report.md)，以便检查具体的检查项。
